# API бэкенда — описание всех ручек (внутренний API изолированного контура)

Базовый URL: `http://127.0.0.1:8000` (фронт ходит через vite-proxy `/api` → бэкенд;
продукт — локальный учебный комплекс без доступа к внешним сетям, см. PLAN §1).
Формат: JSON. Время — ISO 8601 UTC. СУБД целевая — PostgreSQL 12+ (SQLite/`db.db` —
только прототип; сид `public/data/*.json` переезжает в БД при старте).
Внутренний API — только для собственных модулей, внешних интеграций нет;
импорт пакетных обновлений учебных материалов — вручную.

Приведено в соответствие с `PLAN.md` (2026-09-19) и `/workspace/TZ` (ТЗ финал 01.09.2026,
Инструкция по заведению карточки, Памятка АРМ-112 для ДДС, Классификатор v046,
Билеты-задачи, datasheet РТУ Т16Р). Оценки — по рубрике A–F+X (`OPERATOR-CHECKLIST.md`):
веса A 0.10 / B 0.20 / C 0.25 / D 0.20 / E 0.10 / F 0.15; ≥ 80 отлично, 60–79 зачтено,
< 60 или X1–X4/X6 — не зачтено; X5 −50%, X7 −40%. SLA: ответ 8–10 сек (дефолт 8),
карточка 30 сек (дефолт, превышение — красная подсветка).

Решения (зафиксированы + дополнены по PLAN/ТЗ):
- Авторизация — **login/password + номер АРМ без токенов (прототип)**: `POST /api/auth/login`
  возвращает пользователя, фронт хранит его в `localStorage`. Целевое по ТЗ/PLAN:
  многоуровневая аутентификация в локальной сети при каждом входе, автовыход при простое
  (~24 ч), TLS/SSL внутри контура, аудит всех действий, журналы безопасности ≥ 6 мес.,
  RBAC по 3 ролям (см. UI-SPEC §1).
- Фронт **полностью переходит на API**, fallback на `public/data/*.json` нет.
  Статика переезжает в БД через сид при старте.
- Телефония — эмуляция: локальный SIP-сервер + программный IP-телефон + гарнитура
  (ориентир — РТУ Т16Р: 20 SIP-линий, hold/перевод/перехват/АОН/конференция);
  статусы оператора доступен / недоступен / не подключен / ошибка; авто-«недоступен»
  при открытой карточке (+10 сек после закрытия); кнопка «Принять»; `Ctrl+F5` при сбоях;
  СМС-канал в карточке; требования: голос ≤ 150 мс, живучесть до 30 сек, 20 сессий.

Статусы ручек: ✅ есть в `main.py` · ❌ требуется · 🔧 есть, но требует правок.

## 2. Авторизация и сессии (по Инструкции + PLAN §2–3)

### `POST /api/auth/login` ❌ (целевой; прототип — простой login/password)
Проверка логина/пароля (+ номер АРМ) по таблице `users`.

Запрос (прототип; целевое — плюс `arm_number` по Инструкции, Рисунок 1):
```json
{ "login": "umc_operdds1", "password": "dds112-1", "arm_number": "АРМ 4" }
```

Успех (200) — пользователь **без пароля**:
```json
{
  "id": "u-001",
  "login": "umc_operdds1",
  "name": "Иванова Мария Петровна",
  "last_name": "Иванова",
  "role": "student",
  "post": "Оператор ДДС",
  "group": "Группа 1",
  "active": true
}
```

Ошибка (401):
```json
{ "detail": "Неверный логин или пароль" }
```

Неактивный пользователь (403):
```json
{ "detail": "Пользователь деактивирован" }
```

Сид пользователей (роли `student` / `teacher` / `admin` уже есть в таблице `roles`):

| login | password | id | name | role | post |
|---|---|---|---|---|---|
| `umc_operdds1` | `dds112-1` | `u-001` | Иванова Мария Петровна | student | Оператор ДДС |
| `umc_operdds2` | `dds112-2` | `u-002` | Смирнов Алексей Сергеевич | student | Оператор ДДС |
| `umc_teacher` | `teach112` | `u-003` | Кузнецов Никита Андреевич | teacher | Преподаватель |
| `umc_admin` | `admin112` | `u-004` | Соколова Дарья Викторовна | admin | Администратор |

Разделение на фронте: оператор (`student`) видит в Журнале только свои
тренировки, преподаватель/админ — все; `/admin` закрыт только для `admin`.
Целевое по PLAN: RBAC-ограничения (админ не меняет оценки/сценарии во время занятия;
преподаватель не меняет чужие занятия/оценки без аудита; обучающийся без чужих данных);
аудит входов, автовыход ~24 ч, TLS, журналы ≥ 6 мес.

### `POST /api/auth/logout` ❌ (P1)
Завершение сессии + запись в аудит.

### `GET /api/auth/session` ❌ (P1)
Проверка активной сессии.

Нейрогенерация типов происшествий по теме занятия + автоэталон.

Утверждение (validate) / отклонение; поле коррекции (комментарий → пересбор);

### `GET /api/lessons/monitor` ❌ (P1)
Мониторинг realtime: кто на какой карточке, таймеры, завершение/пауза.

## 6. Тренировки: телефония, оценка и результаты (PLAN Блоки 2, 6–8)

### `GET /api/telephony/status`, `POST /api/telephony/answer` ❌ (P1, эмуляция SIP)
Статусы доступен / недоступен / не подключен / ошибка; ручное переключение;
авто-«недоступен» при открытой карточке (+10 сек после закрытия); `Ctrl+F5` при сбоях
(клиентская процедура). Требования: голос ≤ 150 мс, живучесть до 30 сек, 20 сессий.

### `POST /api/sessions/finish` ❌
Главная ручка Симулятора. Принимает итог тренировки, **авторитетно считает
оценку на бэкенде** (контракт §8: A–F+X, веса 0.10/0.20/0.25/0.20/0.10/0.15;
тайминг 8/30, порядок «передача до завершения», запрещённые фразы, грамматика),
сохраняет результат, возвращает его.

Запрос:
```json
{
  "user_id": "u-001",
  "scenario_id": "scn-001",
  "answer_latency_sec": 5.4,
  "messages": [ { "sender": "citizen", "text": "…" } ],
  "form": { "what": "…", "incident_category": "fire", "address": "…" },
  "services": ["fire", "ambulance"],
  "dispatched_at_ms": 1726650000000,
  "ended_at_ms": 1726650200000
}
```

Ответ — объект результата (контракт §7): `session_id`, `scenario_id`,
`rubric_id`, `groups_meta`, `answer_latency_sec`, `messages`, `form`,
`dispatched_services`, `scores`, `total_score`, `verdict`
(`excellent`/`pass`/`fail`), `failed_items` (`id`, `group`, `title`),
`critical_failures`, `detail`.

### `GET /api/results?user_id=...` ❌
Список результатов для Главной (статистика), Списка (средний балл) и Журнала.
Без `user_id` — все (преподаватель/админ), с `user_id` — свои (оператор).
```json
[
  {
    "session_id": "s-2026-001",
    "user_id": "u-001",
    "scenario_id": "scn-001",
    "score": 82.4,
    "verdict": "excellent",
    "date": "2026-09-18T10:03:42Z"
  }
]
```

Поля `session_id`, `score`, `date`, `verdict` обязательны — их читает Журнал.
Таблица Журнала (UI-SPEC §3.5): дата/сценарий/категория/время ответа/время карточки
vs норматив/балл/оценка + фильтры/сортировка; агрегаты для преподавателя.

### `PUT /api/results/{id}/expert` ❌ (P1)
Экспертная оценка и комментарии преподавателя поверх автооценки (с аудитом правок).

### `GET /api/reports/export?format=csv|pdf|json` ❌ (P1)
Экспорт статистики (CSV), документов/сертификатов (PDF), обмена (JSON);
время формирования ≤ 30 сек. Импорт пакетных обновлений — вручную
(`POST /api/admin/import` ❌, P2).

### `GET /api/insights?group=...` ❌ (P2, ИИ-инсайты)
Типичные ошибки группы, тепловые карты ошибок, рекомендации.

### `POST /api/grammar/check` ❌ (P2)
Принудительная проверка грамматики ручного ввода после правок (результат — в отчёт занятия).

## 9. Известные проблемы `main.py` и расхождения с PLAN (очередь 5 — сдача)

1. `app.on_event("startup")` на строке 127 стоит без декоратора —
   `initialize_database()` не вызывается, таблицы/роли не создаются.
2. В таблице `results` нет колонок под `scores`/`messages`/`form`/`verdict`-детали,
   `card_duration_sec`/`sla_*`/`grammar`/`expert` —
   понадобится расширение схемы или отдельная таблица/JSON-поле для объекта результата §7.
3. В таблице `scenarios` нет полей `timeline`, `quick_replies`, `expected`,
   `required_fields`, `classifier_code`, `sla_card_sec`, `validation`, `source` —
   нужны для `GET /api/scenarios/{id}` (JSON-колонки) и конструктора/валидации.
4. Нет таблицы `rubrics` — нужна для раздела 5 (A–F+X).
5. Пароли в `users` хранятся открытым текстом — для учебного стенда допустимо,
   но фиксируем как известное ограничение (целевое — политики паролей + TLS + аудит).
6. Нет ручек телефонии/SIP, уроков/мониторинга, валидации/генерации, экспертной оценки,
   экспорта/инсайтов, грамматики, бэкапа/логов/конфига, ДДС-статусов — требуются по PLAN
   (очереди 1–4). СУБД прототипа SQLite → целевая PostgreSQL 12+.
7. Нефункциональные цели приёмки (очередь 5): отклик ≤ 2 сек при 100 пользователях;
   запись БД ≥ 100 оп/с; отчёт ≤ 30 сек; 20 сессий; голос ≤ 150 мс; живучесть 30 сек.
